# Well-Architected review

This is a review of the pilot light architecture in this repository against the six pillars of the AWS Well-Architected Framework. It is written the way an internal review would be: each pillar lists the decisions actually taken, the trade-offs accepted with reasons, and what would change before running this for real users. Claims reference the Terraform in this repository, not intentions.

A note on honesty. This is a demo-scale deployment on t3.micro instances. Some decisions below are only defensible at demo scale and are flagged as such. Pretending otherwise would defeat the purpose of the review.

## 1. Reliability

The pillar this whole project exists for.

### Decisions taken

- Disaster recovery strategy: pilot light, chosen over backup and restore, warm standby and active-active. The comparison is in [architecture.md](architecture.md); the short version is that pilot light is the cheapest pattern whose RTO is measured in minutes rather than hours.
- Recovery objectives are explicit: RPO under 1 minute, RTO under 30 minutes. Objectives came first, the pattern was chosen to meet them. An organization that cannot tolerate 30 minutes should not build this architecture.
- Within the primary region, the ASG spans two availability zones behind an ALB, so single-instance and single-AZ failures never escalate to a DR event. DR is the last line, not the first.
- Health checking is layered and each layer sees through the one below: the readiness endpoint checks the database, the target group checks readiness, Route 53 checks the target group through the ALB. A failure anywhere in the stack propagates to the DNS decision within about a minute.
- DNS failover is automatic and requires no human. The stateful step, replica promotion, is deliberately manual (argued under operational excellence).
- The secondary DNS record does not evaluate target health, so resolution can flip to a region that is still scaling from zero. The alternative, no answer at all while the pilot light warms, is strictly worse.
- Terraform ignores desired_capacity drift on the ASGs, so a routine apply after a failover cannot scale the promoted region back to zero. This failure mode is easy to create and painful to discover.

### Trade-offs accepted

- Asynchronous replication means non-zero RPO. Writes in flight at the moment of failure are lost. Accepted: synchronous cross-region writes would push write latency from milliseconds to tens of milliseconds for every request, every day, to protect against an event expected less than once a year.
- The RDS primary is single-AZ in this deployment (multi_az = false). At demo scale this halves the database cost; in production it is the wrong choice, because Multi-AZ handles the overwhelmingly more common single-AZ incident without any of the DR machinery. The variable exists and defaults would flip in production.
- Promotion is one way, and failback is a planned project rather than a button. Documented in the runbook rather than hidden.

### What a drill must verify

An untested DR plan is a hypothesis. The [runbook](failover-runbook.md) includes a drill log; the drill that matters end to end is: kill the primary API instances, watch DNS flip unaided, run the script, write a note through the public URL, confirm the X-Serving-Region header shows the secondary.

## 2. Security

### Decisions taken

- Encryption in transit: TLS 1.3 at the ALB with regional ACM certificates, HTTP redirected. Application connections to PostgreSQL run with sslmode=require.
- Encryption at rest: both RDS instances are encrypted with customer managed KMS keys, one per region since keys never leave their region, with rotation enabled. S3 uses SSE-S3.
- Secrets: the database password is generated by Terraform, lives in Secrets Manager, and is replicated natively to the secondary region. Instances fetch it at boot with an IAM policy scoped to that one secret. It never appears in user data, AMIs or the repository.
- No SSH. Instances are managed through Session Manager, port 22 is open nowhere, there are no key pairs. This removes an entire credential class and its rotation burden.
- Network segmentation: instances and databases sit in private subnets. Database security groups accept port 5432 only from the API instance security groups, referenced by ID rather than CIDR. IMDSv2 is enforced.
- The cross-region failover requires no IAM changes at incident time: roles and policies are regional copies deployed in advance, and the operator promoting the replica uses their existing credentials. Nothing about the DR path grants emergency privileges.

### Trade-offs accepted

- S3 uses SSE-S3 rather than KMS. Replicating KMS-encrypted objects needs decrypt and encrypt grants for the replication role on both keys; for non-sensitive demo assets the operational surface was not worth it. With sensitive objects this decision reverses.
- Terraform state contains the database password (any Terraform-managed password does). At demo scale the state is local; in production it belongs in an encrypted S3 backend with tight IAM, or the password moves to Secrets Manager native generation outside Terraform.
- No WAF in front of the ALB. Nothing in a notes demo attracts targeted traffic; a production API adds AWS WAF and rate limiting at the listener.

## 3. Cost optimization

The pillar that justifies pilot light over its alternatives. Full numbers in the [cost analysis](cost-analysis.md).

### Decisions taken

- Compute in the secondary region costs zero between incidents. The ASG sits at zero instances; what remains running is the ALB, the NAT gateway and the RDS replica, all of which shorten RTO enough to earn their keep.
- One NAT gateway per region rather than one per AZ saves roughly 35 USD per region per month. Its failure only degrades instance bootstrap, never live traffic, since inbound flows through the ALB.
- Everything is tagged (Project, ManagedBy, DrPattern) through provider default_tags, so the standby cost is one Cost Explorer filter away and the number in the cost analysis can be verified against a real bill.
- Route 53 health checks use the fast interval plus HTTPS options, roughly 3.50 USD per month. Buying about 20 seconds of detection time for the price of a coffee is the cheapest RTO improvement in the whole design.

### Trade-offs accepted, and one honest admission

- At this demo's scale, pilot light saves little in absolute terms: the secondary region costs about 75 USD per month, and a fully active copy would cost about 100. The pattern earns its keep at production scale, where compute dominates: a fleet of large instances scaled to zero is the difference between a standby region at 20 percent of primary cost and one at 100 percent. The pattern is being demonstrated, not justified, at this scale.
- The secondary ALB and NAT run permanently, about 55 USD per month, purely to shorten RTO. Creating them at failover time would save that money and add 5 to 10 minutes of Terraform apply during the worst possible moment, plus the risk that the apply itself fails. Standby cost was chosen over incident complexity.

## 4. Operational excellence

### Decisions taken

- Everything is code: two regions, replication, DNS policy, alarms. A region can be rebuilt from scratch with terraform apply, which is also the disaster recovery plan for the disaster recovery plan.
- Failover is deliberately semi-automatic. Detection and DNS are automated because they are reversible and safe. Replica promotion is a human decision because it is irreversible and because a wrongly automated promotion (triggered by, say, a health check misconfiguration or a brief network partition) creates a split-brain incident worse than the outage it responds to. The alarm pages a human; the human runs one script.
- The runbook is written for an operator who did not build the system, includes the manual path in case the script is unavailable, and demands a written drill log. The script timestamps every step so drills produce measured RTO, not estimates.
- CI runs terraform validate, the API test suite and shell checks on every pull request, and the repository history itself (small PRs, one concern each) is part of the operational story.

### Trade-offs accepted

- No centralized logging or tracing. CloudWatch agent, structured logs and X-Ray would be the first additions for production; for the DR demonstration they add cost without changing the argument.
- Instances clone the application from GitHub at boot. Simple and transparent for a demo, but it makes boot depend on an external service. Production would bake an AMI (Packer) or pull an image from ECR, both of which also shorten scale-up time.

## 5. Performance efficiency

### Decisions taken

- Writes never cross a region boundary. The application always talks to its local database endpoint, and replication happens behind the scenes. Client write latency is identical to a single-region deployment; the cost of the DR posture is paid in RPO, not in request latency.
- The replica endpoint is identical before and after promotion, so the secondary application needs no reconfiguration, no restart and no DNS change inside the region when the database changes role.
- Failover capacity is a variable, not a constant: the secondary ASG scales to the same size as the primary, from the same launch template, so post-failover performance matches nominal performance by construction.

### Trade-offs accepted

- The secondary region serves nothing in nominal operation. An active-active design would let European users pick the closer region and halve their latency; that benefit is given up in exchange for never having to solve multi-region write conflicts.
- The read replica sits idle instead of serving read traffic. Pointing read-heavy endpoints at it would extract value from a resource that is already paid for, at the cost of the application understanding replica lag. For a notes API the complexity is not worth it; for a read-heavy production system it usually is.

## 6. Sustainability

### Decisions taken

- Scale to zero is the sustainability story as much as the cost story: the standby region consumes compute only during incidents and drills. The carbon footprint of the DR posture is a replica database, an idle ALB and a NAT gateway, not a mirrored fleet.
- Rightsizing by default: t3.micro burstable instances and db.t3.micro match the actual load of a demo instead of provisioning for imagined headroom.
- Both regions run on gp3 storage, and the S3 replica uses the STANDARD class with versioning rather than duplicating into a hotter storage profile than needed.

### Trade-offs accepted

- Cross-region replication itself has a footprint: every byte written is transmitted and stored twice. That is the irreducible physical cost of surviving a regional failure, shared by every DR pattern that replicates data.
- A lifecycle policy expiring old S3 object versions is the obvious next step; versioning without expiry slowly accumulates storage that nobody will read.

## Summary of the honest trade-offs

| Decision | What it buys | What it costs |
| -------- | ------------ | ------------- |
| Pilot light over warm standby | Zero standby compute | 5 to 10 minutes of extra RTO while instances boot |
| Pilot light over active-active | No multi-region write problem | Secondary region idle, RPO above zero |
| Manual promotion | No split-brain from false positives | Human reaction time inside the RTO |
| Async replication | No cross-region write latency | Seconds of data loss at failover |
| Single NAT per region | About 35 USD per region per month | Degraded bootstrap if one AZ loses NAT |
| Single-AZ RDS (demo only) | Half the database cost | Wrong choice for production, flagged as such |
| Keep secondary ALB and NAT warm | Minutes off the RTO, no apply during incidents | About 55 USD per month of standby spend |
